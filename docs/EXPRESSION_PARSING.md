# 表达式解析实现说明

本文档说明 `src/compiler/parser.hpp` 与 `src/compiler/parser.cpp` 中“表达式解析”相关函数的实现方式、调用关系，以及每一种写法背后的设计理由。重点覆盖以下函数：

- `parseExpression`
- `parseOrExpr`
- `parseAndExpr`
- `parseRelationalExpr`
- `parseConcatExpr`
- `parseAdditiveExpr`
- `parseMultiplicativeExpr`
- `parseUnaryExpr`
- `parsePowerExpr`
- `parsePrimaryExpr`
- `parsePostfixExpr`
- `parseTableConstructor`
- `parseFunctionExpr`
- `parseParamList`
- `parseExprList`

同时会顺带解释几个与表达式解析紧密相关的基础设施：`current` / `advance` / `peek` / `match` / `expect`、`RecursionGuard`、`makeExpr`。

## 1. 整体设计：分层递归下降，而不是一张“大优先级表”

当前解析器采用的是“按优先级分层的递归下降”方案。也就是说，不是写一个统一的 `parseBinaryExpression(minPrecedence)`，而是显式拆成多层函数，每一层只处理一组优先级固定的运算符：

```text
parseExpression
  -> parseOrExpr
    -> parseAndExpr
      -> parseRelationalExpr
        -> parseConcatExpr
          -> parseAdditiveExpr
            -> parseMultiplicativeExpr
              -> parseUnaryExpr
                -> parsePowerExpr
                  -> parsePrimaryExpr
                    -> parsePostfixExpr
```

这么实现有几个非常重要的原因：

1. 它和 Lua 参考手册中的优先级模型是一一对应的，读代码时几乎不用做“脑内翻译”。
2. 每层函数只关心自己那一级的运算符，局部逻辑非常清晰，调试时能快速定位是哪一级优先级出了问题。
3. 左结合与右结合可以直接体现在代码结构里：
   - 左结合用 `while` 循环。
   - 右结合用“解析右侧时再次调用当前层函数”的递归。
4. 这种写法天然适合 AST 构造。每消费一个运算符，就能立即把当前左右子树组装成一个节点。
5. 对这个项目来说，Lua 5.1 的表达式集合相对稳定，显式分层比更抽象的 Pratt / precedence climbing 更容易维护。

换句话说，这份实现优先追求的是“语法层次可读性”和“与 Lua 规则的直观对齐”，而不是把所有运算符合并成一个更抽象但更难读的通用框架。

## 2. 表达式解析依赖的基础设施

在进入具体函数前，先明确几个基础工具的职责，因为后面几乎每个解析函数都依赖它们。

### 2.1 `current()` / `advance()`

- `current()` 返回当前 token。
- `advance()` 向前读一个 token。

这种设计的理由是：递归下降解析器最核心的状态就是“当前 token 指针”。把读取状态集中在这两个接口里，能避免每个解析函数都直接操作 `Lexer`，从而保持控制流简单。

### 2.2 `check()` / `match()` / `expect()`

- `check(type)`：只检查，不消费。
- `match(type)`：如果匹配则消费并返回 `true`。
- `expect(type, message)`：如果不匹配就报错。

这三个函数把“看一眼”“有条件地吃掉”“强制要求出现”三类最常见的语法动作分离开了。这样做的原因是：

1. 让语法意图非常直接。看到 `match(',')` 就知道这是可选分隔符，看到 `expect(')')` 就知道这里是硬性闭合。
2. 避免手写重复样板逻辑。
3. 报错路径统一，后续更容易把错误信息风格对齐到 Lua 官方实现。

### 2.3 `peek()`

`peek()` 用于前瞻下一个 token，但不消费当前 token。当前代码里最关键的用途在 `parseTableConstructor()` 中，用来区分：

- `name = value` 这样的记录字段
- `name` 作为普通数组元素表达式

前瞻的价值在于：不必回溯，也不必复制整个 lexer 状态，就能解决局部歧义。

### 2.4 `RecursionGuard`

`parseExpression()`、`parseBlock()`、`parseTableConstructor()`、`parseFunctionExpr()` 里都用了 `RecursionGuard`。

它的意义不是“每进一个函数都计数”，而是“在真正可能造成深层嵌套的入口处计数”。这样做的好处是：

1. 防止恶意或极端输入导致 C++ 调用栈过深。
2. 计数粒度适中，不会因为普通的优先级层级调用而把深度夸大得太严重。
3. 用 RAII 管理进入/退出，异常情况下也能自动回退计数，不容易把状态弄坏。

这是一种很工程化的防御性设计：它不改变语法能力，但能显著提升解析器的稳健性。

### 2.5 `makeExpr()`

所有表达式节点都通过 `makeExpr<T>()` 构造，而不是在各个函数里直接 `std::make_unique`。

原因有三点：

1. AST 节点创建入口统一，调用点更干净。
2. 与 `NodePool<Expr>` 绑定，后续可以统计、调试、优化分配行为。
3. 让“语法规则”和“内存管理”解耦，解析函数只关心语法与 AST 形状。

## 3. 优先级主链：每层函数怎么做，为什么这样做

## 3.1 `parseExpression()`

### 实现方式

`parseExpression()` 是表达式入口函数。它只做两件事：

1. 建立一个 `RecursionGuard`。
2. 直接调用 `parseOrExpr()`。

### 为什么这样实现

这是典型的“顶层入口很薄”的设计。理由是：

1. 表达式真正的优先级入口是最低优先级的 `or`，所以顶层直接落到 `parseOrExpr()` 最自然。
2. 顶层函数越薄，越不容易把优先级逻辑和入口控制逻辑混在一起。
3. 递归深度保护放在这里最合理，因为任何复杂表达式最终都会经过这个入口。

它本质上起的是“总调度器”作用，而不是承担某个具体语法规则。

## 3.2 `parseOrExpr()`

### 实现方式

`parseOrExpr()` 先调用 `parseAndExpr()` 解析左操作数，然后用 `while (match(TokenType::Or))` 不断吸收后续的 `or`：

```text
left = parseAndExpr()
while (遇到 or) {
  right = parseAndExpr()
  left = BinaryExpr(Or, left, right)
}
return left
```

### 为什么这样实现

`or` 是左结合运算符，所以最自然的代码形态就是“先吃一个更高优先级表达式，再循环拼接后续同级运算符”。

这样做的优点：

1. AST 结构天然左折叠，`a or b or c` 会变成 `(a or b) or c`。
2. 每次循环只处理一个同级操作符，代码极易验证。
3. 逻辑运算与算术运算共用同一种二元节点模型，AST 非常统一。

把 `or` 放在最外层，也是因为它在 Lua 中优先级最低。只有等更高优先级的内容都先收敛完，才轮到 `or` 来拼接。

## 3.3 `parseAndExpr()`

### 实现方式

和 `parseOrExpr()` 完全同构：

1. 先解析一个 `parseRelationalExpr()` 作为左侧。
2. 遇到 `and` 就循环构造 `BinaryExpr::Op::And`。

### 为什么这样实现

`and` 也是左结合，而且优先级高于 `or`、低于比较运算。因此它正好位于这两层之间。

分出单独一层而不是把 `and` / `or` 混在一起，有两个直接好处：

1. 能准确体现 Lua 的短路逻辑优先级。
2. 避免出现“同一函数里混合判断两种逻辑运算符”的复杂分支。

这就是分层递归下降的最大价值之一：语法优先级会被直接编码成函数调用顺序。

## 3.4 `parseRelationalExpr()`

### 实现方式

`parseRelationalExpr()` 先解析 `parseConcatExpr()` 作为左侧，然后检查当前 token 是否属于关系运算符集合：

- `<`
- `>`
- `<=`
- `>=`
- `==`
- `~=`

如果是，就：

1. 记录运算符位置。
2. `advance()` 消费运算符。
3. 解析右侧 `parseConcatExpr()`。
4. 构造一个 `BinaryExpr`。

这里使用的是一次性的 `if`，而不是循环。

### 为什么这样实现

这个函数有两个设计意图。

第一，它把“所有比较运算”统一收口到一个地方。这样 AST 中比较表达式始终是同一种节点，只是 `op` 不同。

第二，它当前刻意只消费一个关系运算符。这样做的直接效果是：

- `a < b` 可以解析。
- `a < b < c` 不会在这一层连续折叠成链。

这么做的好处是 AST 非常简单，关系表达式始终是“一个比较节点”，不会出现一串同级比较节点连续拼接的情况。对后续语义处理来说，这很直观，也能避免让读者误以为这里支持类似 Python 那样的“链式比较语义”。

但也必须诚实说明：这同时意味着当前实现比“完全放开左结合比较链”的写法更严格。也就是说，这不是一个“所有可能 Lua 写法都完全等价复现”的最宽松实现，而是一个偏保守的比较层设计。

## 3.5 `parseConcatExpr()`

### 实现方式

`parseConcatExpr()` 先解析左侧 `parseAdditiveExpr()`，如果遇到 `TokenType::Concat`，就递归调用自己去解析右侧：

```text
left = parseAdditiveExpr()
if (遇到 ..) {
  right = parseConcatExpr()
  return BinaryExpr(Concat, left, right)
}
return left
```

### 为什么这样实现

Lua 的字符串连接运算符 `..` 是右结合的，因此不能用 `while` 左折叠。如果写成循环，`a .. b .. c` 会被错误地解析成 `(a .. b) .. c`。

这里采用“当前层递归解析右侧”的写法，正是表达右结合最直接、最可靠的办法：

- `a .. b .. c`
- 先拿到左边的 `a`
- 右边递归得到 `b .. c`
- 最终 AST 是 `a .. (b .. c)`

这类代码非常值得保留，因为它把“结合性”直接体现在函数结构里，比注释更不容易出错。

## 3.6 `parseAdditiveExpr()`

### 实现方式

先解析一个 `parseMultiplicativeExpr()`，然后用 `while` 处理 `+` 和 `-`：

```text
left = parseMultiplicativeExpr()
while (当前是 + 或 -) {
  op = 当前运算符
  advance()
  right = parseMultiplicativeExpr()
  left = BinaryExpr(op, left, right)
}
```

### 为什么这样实现

这是最标准的左结合算术层写法。

理由很充分：

1. `+` / `-` 本来就是同一优先级。
2. 它们都需要先把更高优先级的乘除模表达式整体解析完，再参与组合。
3. 循环写法能自然形成左结合 AST，例如 `a - b - c` 会变成 `(a - b) - c`。

把 `+` 和 `-` 放在同一层，也能避免重复代码；两者唯一差别只是 `BinaryExpr::Op` 取值不同。

## 3.7 `parseMultiplicativeExpr()`

### 实现方式

和加减层相同，只不过处理的是：

- `*`
- `/`
- `%`

左侧、右侧都来自 `parseUnaryExpr()`。

### 为什么这样实现

乘除模同优先级，且左结合，所以与加减层一样用循环处理最自然。

更重要的是，把这一层放在 `parseUnaryExpr()` 之上，意味着：

- 一元表达式会先收敛成完整子树。
- 然后乘除模再把这些子树拼起来。

例如 `-a * b` 中，`-a` 必须先形成一个 `UnaryExpr`，随后乘法层才能正确得到 `(-a) * b`。分层结构正是为了保证这一点。

## 3.8 `parseUnaryExpr()`

### 实现方式

当前支持三个一元运算符：

- `not`
- `-`
- `#`

函数做法是：

1. 如果当前 token 是一元运算符，就立即消费它。
2. 递归调用 `parseUnaryExpr()` 解析操作数。
3. 构造 `UnaryExpr`。
4. 如果当前不是一元运算符，就进入 `parsePowerExpr()`。

### 为什么这样实现

这里最关键的点不是“支持一元运算符”，而是“操作数继续调用 `parseUnaryExpr()`，不是直接调用 `parsePrimaryExpr()`”。

这样设计的好处非常大：

1. 允许多个一元运算符连续出现，例如 `not -#x`。
2. 能正确建立一元运算的右侧嵌套结构。
3. 与 `parsePowerExpr()` 的相对位置一起，确保 `-2^2` 被解析为 `-(2^2)`，而不是 `(-2)^2`。

第三点尤其重要，因为 Lua 中幂运算优先级高于一元负号。当前代码通过“如果没有一元运算符才进入 `parsePowerExpr()`，而一元运算的操作数继续走 `parseUnaryExpr()`”这一组合，实现了正确的优先级关系。

## 3.9 `parsePowerExpr()`

### 实现方式

它先解析一个 `parsePrimaryExpr()` 作为左侧。如果遇到 `^`，就递归调用自己解析右侧，然后构造 `BinaryExpr::Op::Pow`。

### 为什么这样实现

原因和 `parseConcatExpr()` 一样：幂运算是右结合的。

因此：

- `a ^ b ^ c`

必须解析成：

- `a ^ (b ^ c)`

如果这里写成循环，就会变成左结合 AST，这是错误的。

此外，把幂运算放在 `parseUnaryExpr()` 的下一层，还有一个重要效果：它把“幂比一元运算更紧”这件事编码进了调用顺序中。

## 4. 原子表达式与后缀扩展

## 4.1 `parsePrimaryExpr()`

### 实现方式

这个函数负责识别表达式的“原子起点”。当前支持：

- `nil`
- `true`
- `false`
- 数字字面量
- 字符串字面量
- `...`
- 表构造器 `{...}`
- 匿名函数 `function(...) ... end`
- 括号表达式 `(expr)`
- 标识符

每识别出一个原子节点之后，函数几乎都会立刻把结果交给 `parsePostfixExpr(base)`，让后者继续尝试附加：

- 调用
- 索引
- 成员访问
- 方法调用
- 调用语法糖

### 为什么这样实现

`parsePrimaryExpr()` 的任务是“识别起点”，而不是负责整个表达式尾巴。因此它把“起点识别”和“后缀扩展”明确拆成两步：

1. 先构造最小原子节点。
2. 再把它交给统一的后缀处理器扩展成更复杂的前缀/调用链。

这样拆分有明显好处：

1. 结构清晰。原子识别与后缀扩展职责单一。
2. 代码复用高。无论起点是 `name`、`(expr)`、`function(...)` 还是 `{...}`，都能复用同一个后缀处理器。
3. 支持链式结构非常自然，例如 `obj.method()[k]:call("x")`。

当前实现还有一个很值得说明的取舍：它会把包括字面量在内的所有原子表达式都送进 `parsePostfixExpr()`。这种写法的好处是统一，后缀逻辑不需要关心 base 的种类；代价是它在语法层面比 Lua 的“只允许前缀表达式继续接后缀”更宽一些。也就是说，这里选择的是“统一的解析形状”，而不是在 parser 阶段就做最严格的前缀表达式限定。

### 括号表达式为什么单独生成 `ParenExpr`

这里不是简单地返回里面的表达式，而是显式构造 `ParenExpr`。

原因非常关键：Lua 里括号不只是“分组”，还会影响多返回值收敛规则。例如：

- `f()` 可能是多值
- `(f())` 在很多上下文里会被强制收敛为单值

如果解析阶段直接把括号去掉，后续就无法知道这里原来写过括号，也就无法正确实现 Lua 的语义。因此 `ParenExpr` 不是冗余节点，而是语义必要节点。

## 4.2 `parsePostfixExpr(ExprPtr base)`

### 实现方式

这个函数以一个已经解析好的“基础表达式”作为输入，然后反复尝试给它挂接后缀，直到没有更多后缀为止。它使用 `while (true)` 循环，依次处理：

1. `func(args)` 普通函数调用
2. `table[key]` 索引访问
3. `table.member` 成员访问
4. `obj:method(args)` 方法调用
5. `f"string"` 字符串参数调用语法糖
6. `f{table}` 表构造参数调用语法糖

每命中一种形式，就把 `base` 替换成一个新的、更大的 AST 节点，然后继续循环，让后面还能继续接新后缀。

### 为什么这样实现

这是整个表达式解析里最关键的工程设计之一。理由如下：

1. 后缀表达式天然是“无限可链接”的。像 `a.b()[c]:d"x"` 这种形式，如果不用循环，就会写出很多重复且脆弱的嵌套分支。
2. 以后缀循环来扩展 `base`，可以保证解析方向和源码书写顺序一致，阅读起来非常直观。
3. 各种后缀虽然语法不同，但本质上都是“拿旧节点，包成新节点”，因此统一到一个循环里最合适。

### 普通调用 `func(args)`

命中 `(` 后会创建 `CallExpr`，把 `base` 放到 `func` 字段，并用 `parseExprList()` 解析参数列表。

这样设计的原因是调用本质上就是“一个表达式应用到另一组表达式上”，把被调对象本身也表示为 `ExprPtr`，就能支持：

- `f()`
- `obj.method()`
- `(factory())()`
- `function() end ()`

它们在 AST 上都完全统一。

### 索引访问 `table[key]`

命中 `[` 后创建 `IndexExpr`，其中：

- `table` 保存原来的 `base`
- `index` 保存方括号里的表达式

这么做的理由是：Lua 的索引本来就允许任意表达式作 key，所以 `index` 必须是完整表达式，而不能只存字符串或名字。

### 成员访问 `table.member`

命中 `.` 后要求后面必须是名字，并创建 `MemberExpr`。

之所以不把它直接降级成 `IndexExpr(table, "member")`，是因为单独保留 `MemberExpr` 有两个好处：

1. AST 更接近源码原貌，调试时更容易看出用户写的是点访问还是方括号访问。
2. 后续代码生成或优化阶段可以针对成员访问做更直接的处理，而不用先反模式识别字符串 key。

### 方法调用 `obj:method(args)`

这是 Lua 的一个重要语法糖。当前实现分两步：

1. 先把 `obj:method` 变成一个 `MemberExpr`。
2. 再把这个成员表达式包装成 `CallExpr`，并把 `isMethodCall = true`。

这么做非常合理，因为冒号调用本质上仍然是一种“成员访问 + 调用”，只是语义上需要保留“这是冒号语法”这个信息，以便后续阶段处理隐式 `self`。

也就是说，这里没有把 `:` 发明成一种全新的 AST 大节点，而是最大程度复用既有结构，只额外加一个布尔标记。这种设计简单、够用、扩展成本低。

### 调用语法糖 `f"str"` 与 `f{...}`

Lua 允许单参数调用省略括号。当前实现直接在后缀层吸收这两种形式，并构造普通 `CallExpr`：

- `f"abc"` 等价于 `f("abc")`
- `f{a = 1}` 等价于 `f({a = 1})`

之所以把它们放进 `parsePostfixExpr()`，而不是在 `parsePrimaryExpr()` 单独处理，是因为它们本质上不是新的“起点”，而是已有 `base` 之后追加的一种调用尾巴。

## 5. 复合表达式：表构造器与匿名函数

## 5.1 `parseTableConstructor()`

### 实现方式

这个函数负责解析 `{ ... }`。整体流程是：

1. 进入递归保护。
2. 消费 `{`。
3. 循环解析字段，直到遇到 `}`。
4. 消费 `}` 并返回 `TableExpr`。

字段支持三种形式：

1. `[expr] = expr`
2. `name = expr`
3. 单独一个表达式，作为数组部分元素

其中 `TableField` 的表示方式是：

- `key != nullptr` 表示显式键值字段
- `key == nullptr` 表示数组部分字段

### 为什么这样实现

Lua 表构造器本身就混合了“数组部分”和“哈希部分”，因此一个统一的 `fields` 列表是很自然的 AST 形状。这样能保留源码中的字段顺序，而字段顺序对 Lua 是有意义的。

### `[key] = value`

这是最直接的一种情况。key 可以是任意表达式，所以必须调用 `parseExpression()`。

理由很简单：Lua 允许复杂 key，例如：

- `{ [a + b] = v }`
- `{ [f()] = v }`

如果这里只按名字或字符串处理，就会把语法能力砍掉。

### `name = value` 为什么需要 `peek()`

`name` 开头的字段最容易产生歧义：

- 它可能是记录字段 `name = value`
- 也可能只是数组元素表达式 `name`

当前实现通过 `peek()` 看下一个 token 是否为 `=` 来区分两者。这么做有三个优势：

1. 不需要回溯。
2. 判断条件极其稳定，因为 `name =` 的形状很明确。
3. 既保留了 Lua 表构造器的灵活性，又保持了解析器控制流简单。

当识别到 `name = value` 时，代码会把 `name` 转成 `StringExpr` 作为 key。这一做法非常合理，因为 Lua 的 `name = value` 语法糖本质上就是：

```lua
["name"] = value
```

把它在 AST 上显式降解为字符串 key，能让后续阶段只面对一种“键值字段”表示方式。

### 数组部分为什么用 `key == nullptr`

原因是它足够轻量，而且信息完整：

1. 能明确区分“显式键字段”和“顺序数组字段”。
2. 不需要额外引入一个字段类型枚举。
3. 对后续代码生成来说，看到 `nullptr` 就知道这是数组部分，判断成本极低。

### 分隔符为什么允许 `,` 和 `;`，并允许尾随分隔符

这是为了贴合 Lua 语法习惯。尾随分隔符的支持也很重要，因为它能减少用户在多行表构造器里修改最后一项时的摩擦，同时让 parser 更宽容。

## 5.2 `parseFunctionExpr()`

### 实现方式

这个函数负责解析匿名函数：

```lua
function (params) body end
```

流程是：

1. 进入递归保护。
2. 消费 `function`。
3. 解析参数列表 `parseParamList()`。
4. 根据参数列表最后是否为 `"..."` 推导 `isVararg`。
5. 解析函数体 `parseBlock()`。
6. 消费 `end`。

### 为什么这样实现

匿名函数是表达式，不是语句，所以它必须出现在表达式解析链上，而不是只留在语句分支里。

将参数解析和函数体解析拆开，是因为函数头和函数体关注点完全不同：

- 参数列表是 token 级的小结构。
- 函数体是完整 block，会递归回到 statement / expression 体系。

### 为什么 `isVararg` 不直接放在 `parseParamList()` 里决定

当前实现让 `parseParamList()` 返回一个 `Vec<Str>`，如果最后一项是 `"..."`，调用者再把它弹出并设置 `isVararg`。

这么做的原因是复用性更好：

1. `parseParamList()` 可以被函数语句和函数表达式共用。
2. 参数采集逻辑保持简单，只负责“按源码顺序收集参数项”。
3. “最后一项是不是 vararg”属于函数语义整理阶段，留给调用者处理更灵活。

## 6. 两个关键辅助函数

## 6.1 `parseParamList()`

### 实现方式

支持三种情况：

1. 空参数列表：直接遇到 `)`
2. 纯 vararg：`...`
3. 常规参数列表：`name, name, ..., ...`

实现上使用 `do-while` 反复解析参数项，直到没有逗号为止；如果中间遇到 `...`，会把 `"..."` 放入结果并 `break`，表示 vararg 必须是最后一个参数。

### 为什么这样实现

这个函数处理的是一个非常规整的小语法，因此保持“只返回顺序化结果，不做过多解释”是最好的策略。

使用 `"..."` 作为哨兵值也有实际好处：

1. 参数顺序不会丢。
2. 不需要再定义一套参数项 variant。
3. 调用者既可以轻松识别 vararg，也能继续共享同一个容器类型。

## 6.2 `parseExprList()`

### 实现方式

它用一个 `do-while` 解析逗号分隔的表达式列表：

```text
do {
  exprs.push_back(parseExpression())
} while (match(','))
```

### 为什么这样实现

表达式列表在 Lua 里大量出现：

- 函数调用参数
- 赋值右侧
- `return` 返回值
- `for ... in` 迭代表达式

把它抽成独立函数的价值非常高：

1. 消除重复代码。
2. 保证所有“逗号分隔表达式列表”遵循同一套解析规则。
3. 用 `do-while` 可以自然表达“列表至少有一个表达式”这一前提。

它之所以没有处理空列表，是因为调用点已经负责判断是否允许为空。例如函数调用在看到 `(` 后，会先检查下一项是不是 `)`，只有非空才调用 `parseExprList()`。这种分工很合理，因为“是否允许为空”是具体语境的规则，而不是表达式列表本身的规则。

## 7. 这套实现为什么整体上是合理的

把所有细节串起来看，当前表达式解析器有几条很明确的工程思路。

### 7.1 用“函数层级”直接表达“运算符优先级”

这让 parser 的控制流和语法定义高度同构。对维护者来说，看到函数名顺序就能知道优先级顺序，几乎不需要额外文档。

### 7.2 用 `while` 表达左结合，用递归表达右结合

这是递归下降里最朴素、也最不容易出错的做法。`or` / `and` / `+` / `-` / `*` / `/` / `%` 是左结合，`..` / `^` 是右结合，代码结构准确反映了这一点。

### 7.3 原子表达式与后缀扩展分离

`parsePrimaryExpr()` 只负责识别“一个表达式从哪里开始”，`parsePostfixExpr()` 只负责“这个起点后面还能接什么”。这种职责切分大幅降低了复杂度，也让复杂链式表达式的支持变得顺理成章。

### 7.4 AST 形状尽量贴近 Lua 语义，而不是只图解析方便

几个典型例子：

- `ParenExpr` 被保留下来，以承载多返回值收敛语义。
- `MemberExpr` 与 `IndexExpr` 分开，以保留点访问与索引访问的区别。
- `CallExpr` 通过 `isMethodCall` 记录冒号调用语法糖。
- 表字段里的 `name = value` 被降解成字符串 key，统一到同一种键值字段表示。

这说明当前实现不是“只要能过语法就行”，而是有意识地为后续语义阶段、代码生成阶段保留信息。

### 7.5 对复杂输入有基础防御能力

`RecursionGuard` 的存在说明这份实现不仅考虑“正常语法怎么过”，也考虑了“异常输入会不会把解析器拖垮”。这对一个解释器/编译器项目来说非常重要。

## 8. 当前实现中几个值得特别注意的取舍

为了让读者对代码有准确认知，最后把几个实现选择单独列出来。

### 8.1 关系运算当前只解析一个比较操作符

`parseRelationalExpr()` 用的是单次 `if`，不是循环。因此当前实现把关系表达式固定成一个二元比较节点，而不是比较链。

好处是 AST 简单、语义清晰；代价是它更保守。

### 8.2 所有原子表达式都会进入 `parsePostfixExpr()`

这让后缀处理器非常统一，但也意味着 parser 阶段对“哪些 base 真正允许接后缀”没有做最严格限制。当前实现更偏向“先把结构解析出来，再由后续阶段决定是否合法”。

### 8.3 一些节点的位置记录是“结构起点导向”的

大部分构造函数都会在进入分支时记录 `line/column`，目的是让 AST 节点能定位到该语法结构出现的位置。当前部分运算符分支在 `match()` 之后才取位置，因此拿到的是消费运算符后的当前位置。这是当前代码的具体行为，理解这一点有助于后续排查定位信息时不产生误判。

## 9. 总结

当前表达式解析实现的核心价值，不在于用了多复杂的技巧，而在于它把 Lua 表达式语法拆成了一条非常清晰的责任链：

- 低优先级函数负责拼接高优先级结果
- 左结合靠循环
- 右结合靠递归
- 原子与后缀分离
- 复合结构通过辅助函数处理歧义与语法糖

这使得 parser 同时具备了三种重要特性：

1. 容易读，函数名就能反映语法层次。
2. 容易扩展，新增一层或新增一种后缀都比较局部。
3. 容易生成 AST，且 AST 形状对后续语义阶段友好。

如果后续要继续演进这套解析器，这份结构仍然是一个很好的基础，因为它已经把“优先级”“结合性”“语法糖”“语义保真”这几个编译器前端里最容易纠缠在一起的问题，分得比较清楚了。
