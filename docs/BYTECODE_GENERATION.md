# Lua 字节码生成设计说明

本文基于 `src/compiler/codegen.hpp` 与 `src/compiler/codegen.cpp` 两个文件，系统说明当前项目中的 Lua 字节码生成器是如何工作的。目标不是简单罗列函数，而是把“为什么这样设计”“每一步在解决什么问题”“哪些地方最容易出错”讲清楚。

这份文档适合三类读者：

- 想快速理解 `CodeGenerator` 整体结构的维护者
- 想定位寄存器错乱、跳转回填、闭包捕获等问题的调试者
- 想继续补齐 Lua 5.1 代码生成细节的开发者

---

## 1. 先说结论：这个代码生成器在做什么

`CodeGenerator` 的职责可以概括成一句话：

> 把 AST 里的“语法结构”，翻译成 `Proto` 中的“指令流 + 常量表 + 子函数原型 + 调试信息”。

它做的不是解释执行，也不是语义分析，而是把已经解析好的语法树变成 VM 可以直接执行的字节码。

在这个实现里，代码生成器需要同时管理 5 件事：

1. 指令发射：把高级语义翻译成 `LOADK`、`CALL`、`JMP`、`SETTABLE` 等指令。
2. 寄存器分配：决定每个表达式、参数、临时值、局部变量放在哪个寄存器。
3. 常量收集：把数字、字符串、布尔值等放进 `Proto` 的常量表。
4. 跳转回填：先发射占位 `JMP`，等目标位置确定后再修补偏移。
5. 调试元数据：记录源码行号、局部变量生命周期、upvalue 名称。

如果把编译过程看成流水线，大致是这样：

```text
AST
  -> expr()/statement() 递归遍历
  -> 维护 ExprDesc / freereg_ / nactvar_ / jpc_
  -> 发射 Proto 指令
  -> 回填跳转和元信息
  -> 得到可执行 Proto
```

---

## 2. 生成结果是什么：Proto 视角

虽然本文主要分析 `codegen`，但理解它时一定要记住，最终产物是 `Proto`。

从 `codegen.cpp` 的调用方式可以看出，当前生成器会往 `Proto` 里写入这些信息：

- 指令序列：`addInstruction()`
- 行号表：`addLineInfo()`
- 常量表：`addConstant()`
- 子函数原型：`addProto()`
- 局部变量调试信息：`addLocVar()`
- upvalue 名称：`addUpvalueName()`
- 若干函数属性：`maxStackSize`、`numParams`、`isVararg`、`linedefined`、`lastlinedefined`

也就是说，`CodeGenerator` 不只是“发指令”，它其实在组装一整个函数原型对象。

## 3. 核心状态：理解 codegen 的钥匙

看 `CodeGenerator` 最容易迷路的地方，是它有不少内部状态。实际上只要抓住几个关键字段，整个实现就会清晰很多。

### 3.1 `proto_`

当前正在生成的函数原型。

- 顶层 chunk 调用 `generate()` 时会新建一个 `Proto`
- 遇到函数表达式 / 函数语句时，会通过 `compileFunction()` 递归生成新的子 `Proto`

可以把它理解为“当前输出文件”。所有 `codeABC()` / `codeABx()` / `codeAsBx()` 都是往这个对象里写内容。

### 3.2 `freereg_`

第一个空闲寄存器，也就是“下一个临时值可以放到哪里”。

这是整个生成器最重要的运行时状态之一。

- `allocReg()`：分配一个寄存器并前移 `freereg_`
- `freeReg()`：在满足条件时回收寄存器
- `checkStack(n)`：保证 `freereg_ + n` 不超过当前 `Proto` 的 `maxStackSize`

可以把寄存器想成一段线性工作区：

```text
[ 活跃局部变量 ][ 当前表达式临时值 ][ 空闲区 ... ]
               ^
             freereg_
```

### 3.3 `nactvar_`

当前“活跃局部变量”的数量。

它与 `freereg_` 的关系很关键：

- `0 .. nactvar_-1` 通常对应当前作用域内必须保留的局部变量寄存器
- `nactvar_ .. freereg_-1` 通常是临时寄存器

所以本生成器默认遵守一个基本规则：

> 任何语句结束后，临时寄存器都应尽量回收到 `nactvar_` 之后。

这也是很多“寄存器被覆盖”类 bug 的根源和修复入口。

### 3.4 `localVars_`

局部变量调试信息表，元素类型为 `LocalVar`。

每个局部变量记录：

- 名字 `name`
- 所在寄存器 `reg`
- 生效起点 `startpc`
- 生命周期终点 `endpc`

它既参与名字解析，也用于最终调试信息写回。

### 3.5 `upvalues_`

当前函数捕获到的 upvalue 列表，元素类型为 `UpvalueCapture`。

每个 upvalue 需要记录三件事：

- `name`：变量名，主要用于调试和可读性
- `inStack`：捕获来源是不是父函数的局部变量
- `index`：来源索引。若 `inStack=true`，是父函数寄存器索引；否则是父函数 upvalue 索引

这份信息最后用于在 `CLOSURE` 后发射伪指令：

- 来自父局部变量：发 `MOVE`
- 来自父 upvalue：发 `GETUPVAL`

### 3.6 `jpc_`

待处理跳转链表。

这是 Lua 代码生成中一个非常经典、也非常容易被忽视的技巧。很多跳转在发射时并不知道目标地址，所以先串成链表，等到真正到达目标点时再统一回填。

当前实现中的关键规则是：

> 每次真正发射新指令前，都先调用 `dischargejpc()`，把待处理跳转补到“当前位置”。

这也是 `codeABC()` / `codeABx()` / `codeAsBx()` 开头都先做一次 `dischargejpc()` 的原因。

### 3.7 `currentBlock_`

当前语句块信息，类型是 `BlockInfo`，用于管理：

- 进入块时的活跃变量数
- 该块是否允许 `break`
- 该块内所有 `break` 的跳转链表

它主要支撑 `while`、`for`、`do ... end` 以及局部作用域离开时的清理。

### 3.8 `forcedCallBase_`

这是当前实现中一个很实用的工程化字段，不是“教科书上必然存在”的状态。

它的用途是：

> 当某些上下文要求函数调用的返回值必须落在某个指定寄存器区域时，临时强制 `CallExpr` 以那个基址布局。

最典型的使用场景是表构造器最后一个数组字段支持多返回值展开。

### 3.9 `currentLine_`

当前发射指令对应的源码行号。

`expr()` 和 `statement()` 在进入节点时会先更新 `currentLine_`，而 `codeABC()` / `codeABx()` / `codeAsBx()` 在发射指令后立即调用 `addLineInfo(currentLine_)`。这使得最终字节码能保留比较完整的源码行映射。

## 4. `ExprDesc`：表达式生成的中间语言

如果说 `freereg_` 是代码生成的“地面调度”，那 `ExprDesc` 就是代码生成的“交通标识”。

它的作用不是保存 AST，而是描述“这个表达式当前处于什么状态”。

### 4.1 为什么需要 `ExprDesc`

因为同一个表达式，在不同阶段可能有完全不同的存在形式。例如：

- 常量 `123`：可以暂时只记成一个数字，而不立即发 `LOADK`
- 局部变量 `a`：可能已经在寄存器里，无需生成指令
- 全局变量 `x`：还没真的读取，只是记录了常量表中的名字索引
- 表达式 `t[k]`：可能暂时只是“一个索引访问”，还没真正 `GETTABLE`
- 函数调用 `f()`：结果已经在寄存器里，但相关的 `CALL` 指令位置还要保留以便后续修改返回值个数

如果没有 `ExprDesc`，生成器就会被迫“见到节点就立刻发死指令”，那样既低效，也很难支持 Lua 的多返回值语义。

### 4.2 `ExprKind` 的核心意义

当前实现里的 `ExprKind` 可以按用途分成几组。

#### 1) 常量类

- `Nil`
- `True`
- `False`
- `Number`
- `Const`

这类表达式还没有固定落地到寄存器，属于“可延迟物化”的值。

#### 2) 变量/位置类

- `Local`
- `Upval`
- `Global`
- `Indexed`

这类表达式重点不是“值是多少”，而是“值从哪里来、将来写回到哪里”。

#### 3) 结果位置类

- `NonRelocatable`
- `Relocatable`

这是 Lua 代码生成最关键的一对状态：

- `NonRelocatable`：值已经在某个固定寄存器里
- `Relocatable`：值对应的指令已经发出，但结果寄存器还可以改写

举例：

- `GETGLOBAL 0 k` 若 A 还没最终确定，就可以先记成 `Relocatable`
- 真正要把它放到某个寄存器时，再通过 `discharge()` 修改指令 A 字段

#### 4) 控制流类

- `Jump`

它表示这个表达式的真假不是现成的寄存器值，而是由一段跳转逻辑控制。

比较运算最典型：

```lua
a < b
```

它往往先编译成“比较指令 + 跳转”，而不是先计算出 `true/false` 放入寄存器。只有在确实需要一个布尔值时，才会再物化成 `LOADBOOL`。

#### 5) 特殊多返回值类

- `Call`
- `Vararg`

这两类是 Lua 代码生成最麻烦的点，因为它们既可以表现为一个值，也可以表现为多个值。

因此当前实现会保留更多信息：

- `Call`：`info` 保存调用基址，`aux` 保存 `CALL` 指令 PC
- `Vararg`：`info` 保存 `VARARG` 指令 PC

这样后续语句可以回头修改 `CALL` 的 `C` 参数或 `VARARG` 的 `B` 参数，让它们返回 1 个值、多个值，或者全部值。

### 4.3 `ExprDesc` 的三个常用变换

理解下面三个函数，基本就掌握了表达式生成主线。

#### `luaK_dischargevars(desc)`

把“变量访问语义”变成“真正的取值动作”。

例如：

- `Global` -> 发 `GETGLOBAL`，转为 `Relocatable`
- `Indexed` -> 发 `GETTABLE`，转为 `Relocatable`
- `Upval` -> 发 `GETUPVAL`，转为 `Relocatable`
- `Call` / `Vararg` -> 修改返回值数量，收敛为单值语义

#### `exp2Val(desc)`

保证该表达式以“单值”语义存在。

它主要解决一个 Lua 特有问题：

> `f()` 和 `...` 在有些位置可以返回多个值，但在大多数表达式上下文里必须被收敛成 1 个值。

#### `discharge(desc, reg)`

把表达式真正落到指定寄存器 `reg`。

它会根据 `ExprKind` 选择不同策略：

- 常量：发 `LOADK` / `LOADBOOL` / `LOADNIL`
- `Local` / `NonRelocatable`：必要时发 `MOVE`
- `Relocatable`：直接改写原指令的 A 字段
- `Call`：不能直接改 A，只能在必要时补 `MOVE`
- `Jump`：补成显式布尔值

这也是为什么 `discharge()` 是整个文件里最值得反复阅读的函数之一。

## 5. 指令发射层：三种编码函数的真实职责

生成器有三种底层发射接口：

- `codeABC()`
- `codeABx()`
- `codeAsBx()`

表面上它们只是对应不同指令编码格式，实际还承担两个隐含职责：

### 5.1 自动修补 `jpc_`

每次发新指令前都先 `dischargejpc()`，把所有“应该跳到当前位置”的待处理跳转修好。这是控制流正确性的基础。

### 5.2 自动记录源码行号

每次发射完指令后都 `addLineInfo(currentLine_)`，保证 VM / 调试器后续能知道指令来自源码哪一行。

换句话说，`codeABC()` 等函数不是简单的“构造一条指令”，而是“按当前代码生成状态安全地发射一条指令”。

## 6. 寄存器模型：这份实现最核心的部分

Lua 5.1 VM 是寄存器型虚拟机，所以几乎所有代码生成问题，最终都会变成寄存器布局问题。

### 6.1 当前实现的基本约定

一个函数内的寄存器通常按下面方式使用：

```text
R(0) ... R(nactvar_-1)          活跃局部变量
R(nactvar_) ... R(freereg_-1)   临时寄存器
R(freereg_) ...                可分配区
```

### 6.2 `allocReg()` / `freeReg()` 的设计意图

这套分配器非常简单，不做图着色，也不做复杂活性分析，而是采用“线性前进，末尾回收”的策略。

优点：

- 实现直接
- 易于与 Lua 原始实现对齐
- 调试相对容易

代价：

- 稍不注意就会出现“中间寄存器还在用，但尾部被错误回收”的问题
- 需要靠大量局部约定维持正确性

### 6.3 为什么 `checkStack()` 很重要

生成器里有不少地方在修改 `freereg_`，但实际 VM 运行时是否安全，取决于 `Proto::maxStackSize` 是否同步增长。

所以本实现在很多看似“多余”的地方补了 `checkStack(0)` 或 `checkStack(n)`，其目的不是当前就要分配寄存器，而是确保：

> 字节码执行时，VM 为该函数预留的栈空间足够大。

这也是文档和代码注释里多次把它标为 P0 修复的原因。

### 6.4 为什么很多语句末尾要把 `freereg_` 收回到 `nactvar_`

因为表达式求值阶段会产生各种临时寄存器，如果这些寄存器不及时释放，下一条语句就可能把它们误当成“还在使用的值”，或者更糟，错误覆盖真正的局部变量。

典型例子是语句级函数调用：

- `print("x")` 的返回值没人接
- 这条语句结束后，其调用帧相关临时寄存器都不该继续保留

所以 `emitStmt(const CallStmt&)` 最后明确把 `freereg_ = nactvar_`。

## 7. 名字解析：局部、upvalue、全局三层查找

`emitExpr(const NameExpr&)` 的策略很清晰：

1. 先查局部变量 `findLocalVar()`
2. 再查 upvalue `resolveUpvalue()`
3. 都找不到就当作全局变量

这正对应了 Lua 的典型静态解析顺序。

### 7.1 局部变量

`findLocalVar()` 从后往前找，保证内层作用域优先。

找到后返回对应寄存器，表达式记为 `ExprKind::Local`。

### 7.2 Upvalue

`resolveUpvalue()` 的逻辑非常值得看：

- 如果没有父生成器，说明已经到最外层，不存在 upvalue
- 先看父函数的局部变量里有没有这个名字
- 如果没有，再递归让父函数去解析它自己的 upvalue

这样就实现了闭包的逐层穿透捕获。

举个直观例子：

```lua
function outer()
  local x = 1
  function middle()
    function inner()
      return x
    end
  end
end
```

`inner` 并不是直接从 `outer` 的局部表里读 `x`，而是让 `middle` 先建立一个中转 upvalue，再由 `inner` 捕获 `middle` 的 upvalue。

### 7.3 全局变量

如果局部和 upvalue 都没命中，就把名字放进常量表，表达式记为 `Global`。真正取值时再由 `luaK_dischargevars()` 发 `GETGLOBAL`。

这种延迟设计的好处是：

- 访问位置可以晚一点再决定
- 如果该名字出现在赋值左侧，还能复用同一套变量描述

---

## 8. 常量生成：尽量晚落地，必要时再装入寄存器

生成器对常量的处理很典型：

- 数字：`numberConstant()`
- 字符串：`stringConstant()`
- 布尔：`boolConstant()`
- nil：`nilConstant()`

但注意，表达式阶段并不会总是马上把它们装进寄存器，而是先用 `ExprDesc` 记录。

这带来两个好处：

1. 某些常量可以直接走 RK 操作数，无需 `LOADK`
2. 直到真正需要寄存器时，才做最少量的物化

---

## 9. RK 机制：为什么有些常量不用先 `LOADK`

`exp2RK()` 是 Lua 指令生成里一个非常重要的优化接口。

它的思路是：

> 如果一个操作数既可以来自寄存器，也可以直接来自常量表，那就优先编码成 RK 形式，减少额外 `LOADK`。

例如算术指令、比较指令、表访问里的 key/value，很多都支持 RK。

函数 `exp2RK()` 的行为可以概括为：

- 如果是数字常量且索引不超过 `MAXINDEXRK`，直接返回 `RKASK(k)`
- 如果本来就是常量表项且索引允许，也直接返回 RK
- 否则退化为把表达式放入寄存器，返回寄存器编号

这类优化看似小，但会显著减少字节码体积。

## 10. 表达式生成主线

### 10.1 字面量与基础表达式

- `NilExpr` -> `ExprKind::Nil`
- `BoolExpr` -> `True` / `False`
- `NumberExpr` -> `Number`
- `StringExpr` -> 字符串常量表索引，记为 `Const`
- `ParenExpr` -> 先 `exp2Val()` 收敛多返回值，再保证在寄存器中

这里最值得注意的是括号表达式。Lua 5.1 里：

```lua
f()      -- 可能多返回值
(f())    -- 必须收敛成单值
```

当前实现明确在 `emitExpr(const ParenExpr&)` 里保留了这个语义。

### 10.2 变量、索引、成员访问

#### `NameExpr`

如前所述，先解析成 `Local` / `Upval` / `Global` 三者之一。

#### `IndexExpr`

生成 `table[key]` 的访问语义时，代码先做三件事：

1. 计算表表达式
2. 强制表表达式进入寄存器
3. 计算 key，并通过 `luaK_indexed()` 把表达式标记成 `Indexed`

这里的关键点是：

> 表表达式必须真正位于寄存器中，不能只停留在 `Relocatable` 状态。

原因很简单，后续 `GETTABLE` / `SETTABLE` 的 B 操作数需要的是“表所在寄存器”。

#### `MemberExpr`

本质上是 `table["member"]` 的语法糖。

所以实现和 `IndexExpr` 几乎相同，只是 key 直接是字符串常量。

### 10.3 函数调用 `CallExpr`

这是整个文件最复杂的一块之一。

Lua 的调用约定要求：

- 被调函数放在寄存器 `base`
- 参数必须连续放在 `base+1`, `base+2`, ...
- `CALL` 指令的 A 就是这个 `base`

当前实现为保证这一点，做了几步非常关键的处理。

#### 第一步：确定函数基址 `base`

- 普通调用：先求值函数表达式，再 `exp2AnyReg()`
- 方法调用 `obj:method(args)`：使用 `SELF` 指令，一次性把函数和隐式 `self` 摆到正确位置

`SELF A B C` 的效果是：

- `R(A+1) = R(B)`，也就是把对象复制为 `self`
- `R(A) = R(B)[RK(C)]`，也就是取出方法

这正好给后续 `CALL A ...` 准备好了调用布局。

#### 第二步：必要时搬移函数基址

如果当前 `base` 太低，可能会覆盖外层表达式还在使用的寄存器；如果上下文要求调用结果必须对齐到某个固定位置，还要支持强制基址。

所以实现里引入了两种调整：

- `forcedCallBase_ >= 0`：把函数及其隐式 `self` 搬到指定基址
- `base < savedFreeReg`：把调用整体搬到更安全的高位寄存器区域，防止嵌套调用污染外层寄存器

这部分可以理解成“给调用帧找一块连续、干净、不会踩别人的寄存器区域”。

#### 第三步：显式参数必须连续排布

当前实现不是简单让每个参数自己找寄存器，而是：

- 把 `freereg_` 人为设到参数起点
- 对每个参数求值后，强制写入 `firstArgReg + i`

这样做是为了规避一个非常典型的嵌套调用 bug：

```lua
print(type(print))
```

如果参数寄存器不是连续的，外层 `CALL` 会按约定去 `base+1` 开始读参数，但真正的参数可能被内层调用临时值打散到别处，结果就是调用参数错位。

#### 第四步：发 `CALL`

当前实现默认生成：

```text
CALL base (nargs+1) 2
```

其中 `C=2` 表示默认期待 1 个返回值。

之所以不是最终值，是因为后续不同上下文还可能改它：

- 作为普通表达式时，通常保留单值
- 作为语句时，会改成 `C=1`，表示丢弃返回值
- 作为多返回值上下文时，会改成 `C=0` 或具体需要的返回值个数

#### 第五步：调用结束后的寄存器恢复

调用完成后，生成器不会把整个调用区域永久保留，而是把 `freereg_` 收回到：

- 至少 `base + 1`
- 但不能低于外层已保留的 `savedFreeReg`

这是为了同时满足两件事：

- 保留返回值寄存器
- 不破坏外层表达式仍在使用的寄存器布局

#### 为什么 `Call` 的 `ExprDesc` 要同时保存 `base` 和 `pc`

因为后续会有两种完全不同的修改需求：

- 需要知道返回值在哪个寄存器区开始：用 `info = base`
- 需要回头修改 `CALL` 指令本身：用 `aux = pc`

这正是多返回值语义能正常工作的关键。

### 10.4 `VarargExpr`

`...` 的实现思路与 `CallExpr` 类似，也是先生成一条可回头修改的指令：

```text
VARARG A B
```

初始时：

- `A=0`，稍后可重定位
- `B=1`，默认语义接近“暂时不扩展，等待上层决定需要几个值”

如果后续进入单值上下文，`luaK_dischargevars()` 会把它改成只返回 1 个值；若进入多返回值上下文，则会改成需要的个数，甚至返回全部值。

### 10.5 二元表达式

#### 算术运算

如 `+ - * / % ^`，通过 `codearith()` 统一生成。

大致流程：

1. 把左右操作数转成 RK 或寄存器
2. 发对应算术指令
3. 把结果记为 `Relocatable`

这意味着结果寄存器还可以被后续指定。

#### 字符串连接

`CONCAT` 比一般算术更特殊，因为它要求参与连接的值在连续寄存器区间内，所以实现中会对左右操作数调用 `exp2NextReg()` 而不是简单 RK 化。

#### 比较运算

比较不是直接得到布尔寄存器值，而是通过 `codecomp()` 生成：

- 比较指令 `EQ/LT/LE`
- 后接一个 `JMP`

结果被标记为 `ExprKind::Jump`。

这非常符合 Lua 官方实现风格，也能让 `if` / `while` 这类控制流直接复用已有跳转，而不是先多做一次布尔物化。

#### `and` / `or`

逻辑短路是这份实现里很值得肯定的一块。它没有把逻辑运算粗暴降级成单纯的布尔运算，而是按 Lua 语义保留“返回原值”的特征。

以 `and` / `or` 为例，当前实现的思路是：

1. 先把左值收敛成单值
2. 分配一个结果寄存器 `resultReg`
3. 先把左值写进去
4. 用 `TEST + JMP` 判断是否需要跳过右值
5. 若右值需要执行，则让右值覆盖写回同一个结果寄存器

这套策略解决了两个常见坑：

- 短路分支读到未初始化寄存器
- 右值求值覆盖仍活跃的局部变量寄存器

### 10.6 一元表达式

#### 负号 `-`

实现中特别处理了 `-(数字常量)`，直接把它优化成负数常量，而不是生成运行时 `UNM`。

这个修复很有针对性，主要是为了兼容像 `arg[-1]` 这样的写法，避免把负数字面量误编译成更绕的运行时表达式。

#### `not`

通过 `codenot()` 处理：

- 对常量直接折叠
- 对 `Jump` 通过 `invertJump()` 反转跳转条件
- 否则发 `NOT`

#### `#`

长度运算先确保操作数进入寄存器，再走统一算术生成路径。

## 11. 赋值与局部声明：为什么这两者要分开看

Lua 中：

- `a = b` 是“把值写到已有位置”
- `local a = b` 是“先分配新局部槽位，再初始化”

这两类操作在字节码层的处理差别很大。

### 11.1 普通赋值 `AssignStmt`

核心入口是 `luaK_storevar()`，它根据左值类型选择不同写回方式：

- `Local`：直接写到对应寄存器
- `Upval`：发 `SETUPVAL`
- `Global`：发 `SETGLOBAL`
- `Indexed`：发 `SETTABLE`

这就是为什么赋值语句中会先把左值也用 `expr()` 求出来。因为这里的 `expr()` 不是单纯“求值”，而是在构造一个“可写目标描述符”。

### 11.2 局部变量声明 `LocalStmt`

这是另一个极易出 bug 的区域。

当前实现的关键策略是：

#### 1) 先记住 `base = nactvar_`

这表示“新局部变量应该从哪个寄存器开始排”。

#### 2) 先预分配局部槽位，再回退 `freereg_`

代码会先 `addLocalVar()` 为每个名字登记寄存器，但随后把 `freereg_` 重设回 `base`。这样右值表达式在求值时，就能从局部目标寄存器区开始布局。

这一步非常重要，因为 Lua 的局部初始化不是“先在别处算完，再整体搬过来”，而是倾向于让结果直接落在未来局部变量所在的位置。

#### 3) 最后一个表达式可能是多返回值

这正是 `local a, b, c = f()` 之类语义的核心。

当前实现中：

- 如果最后一个表达式是 `Call` 或 `Vararg`
- 会根据“剩余变量数量”回头修改 `CALL/VARARG` 指令的返回值个数
- 必要时再补 `MOVE`，把返回值搬到目标局部槽位

特别值得注意的是：

> 对 `Call` 不能直接改 `CALL` 指令的 A 参数。

因为 `A` 不只是“返回值放哪”，它还是“函数和参数区的调用基址”。直接改 A 会破坏调用布局，VM 就会从错误寄存器取函数和参数。

这也是代码里专门强调的 P0 修复点。

#### 4) 没有被初始化到的局部变量补 `LOADNIL`

如果右值数量不足、且最后一个表达式不是会扩展的多返回值，就补：

```text
LOADNIL base+nexps, base+nvars-1
```

让剩余局部变量全部初始化为 `nil`。

## 12. 返回语句：本质上也是一组寄存器布局

`emitStmt(const ReturnStmt&)` 的策略相对直接：

- 无返回值：`RETURN 0 1 0`
- 有返回值：从 `base = nactvar_` 开始布置返回值寄存器，然后发 `RETURN base, nret+1, 0`

这里要注意两个点：

1. 返回值寄存器区不与当前局部变量区冲突，直接从 `nactvar_` 后开始临时使用
2. 在写返回值前会先 `checkStack(nret)`，确保 `maxStackSize` 足够

当前实现对“返回最后一个多返回值表达式”的 Lua 细节没有展开做专门分支，但整体框架已为此类扩展留好了位置。

## 13. 控制流生成：跳转链表如何串起来

控制流部分最核心的思想只有一句话：

> 先发占位跳转，再在目标点出现时统一回填。

### 13.1 `jump()`、`patchList()`、`patchtohere()`

- `jump()`：生成一条占位 `JMP`
- `patchList(list, target)`：把链表中的每个跳转都补到目标点
- `patchtohere(list)`：把某条链表记为“应该跳到当前位置”，并通过 `jpc_` 延迟到下次发指令前再修补

其中 `patchtohere()` 很关键，因为很多时候“当前位置”还会继续被新指令推进，采用 `jpc_` 延迟修补可以更接近 Lua 官方实现语义。

### 13.2 条件跳转的辅助函数

#### `luaK_goiftrue()`

把表达式转成“假时跳走”的形式。非常适合 `if cond then ...` 这种结构。

#### `luaK_goiffalse()`

把表达式转成“真时跳走”的形式。主要用于 `or` 的短路逻辑。

#### `jumponcond()` / `condjump()`

这是把“一个一般表达式”落地成 `TEST/TESTSET/JMP` 组合的地方。

代码里对 `TESTSET + NO_REG` 做了一个很重要的修复：

- 如果目标寄存器是 `NO_REG`
- 就不能发 `TESTSET`
- 必须退化成 `TEST`

否则会在 VM 执行阶段使用无效寄存器编号。

### 13.3 比较表达式的布尔物化

比较表达式通常先变成 `Jump`，但如果真的要把结果作为普通值使用，例如：

```lua
local x = (a < b)
```

那 `discharge()` 里会把它物化成：

```text
LOADBOOL reg false 1
LOADBOOL reg true 0
```

并把“真分支跳转”修补到第二条 `LOADBOOL`。

这实际上就是用两条指令把“控制流结果”转换成“寄存器中的布尔值”。

## 14. `if` / `elseif` / `else` 的生成思路

`IfStmt` 的实现非常接近 Lua 官方思路。

整体上维护两条链：

- `flist`：当前分支条件为假时去哪里
- `escapelist`：已执行完某个分支后，跳过后续分支和 else 的出口链表

大致模式如下：

```text
if cond1 then
  block1
elseif cond2 then
  block2
else
  block3
end
```

生成策略是：

1. 为 `cond1` 生成假分支跳转 `flist`
2. 编译 `block1`
3. 发一个 `jump()` 加入 `escapelist`，用来跳过后续分支
4. 把 `flist` 补到下一个分支开头
5. 对 `elseif` 重复同样过程
6. 若有 `else`，把最后一个 `flist` 补到 `else` 开头
7. 最终把 `escapelist` 全部补到 if 结构末尾

当前实现还做了一层优化：

- 如果条件本身是比较表达式，直接发 `EQ/LT/LE + JMP`
- 否则走一般条件表达式流程

这减少了不必要的布尔中间值。

---

## 15. `while` 的生成思路

`while` 结构本质上是：

```text
whileinit:
  if not cond then goto exit
  body
  goto whileinit
exit:
```

当前实现中的关键点：

1. `whileinit = getLabel()` 记录循环起点
2. 生成条件，得到“条件为假时退出”的 `condexit`
3. `enterBlock(true)` 进入可 `break` 块
4. 编译循环体
5. 发回跳到 `whileinit`
6. `leaveBlock()` 修补 `break`
7. 把 `condexit` 补到循环结束位置

其中 `leaveBlock()` 负责把该块内所有 `break` 统一导向循环出口，这使 `break` 的实现变得非常自然。

---

## 16. `for` 循环：两类循环，两套寄存器约定

Lua 的 `for` 有两种：数值 `for` 和泛型 `for in`。两者在字节码层差异很大。

### 16.1 数值 `for`

当前实现采用 Lua 5.1 常见布局：

- `R(base)`：当前索引
- `R(base+1)`：上界
- `R(base+2)`：步长
- `R(base+3)`：对 Lua 代码可见的循环变量

字节码模式大致是：

```text
FORPREP base ...
body
FORLOOP base ...
```

实现中特别注意了一点：

> 会把 3 个内部控制变量和 1 个可见循环变量都登记为局部变量。

这样做不是形式主义，而是为了保证：

- `nactvar_` 正确覆盖这些保留寄存器
- 后续语句不会误把这些寄存器当成可随意复用的临时寄存器

### 16.2 泛型 `for in`

典型布局：

- `R(base)`：迭代器函数
- `R(base+1)`：状态
- `R(base+2)`：控制变量
- `R(base+3...)`：可见循环变量

当前实现要求迭代器表达式必须是函数调用，并且返回 3 个值，这与 `pairs(t)`、`ipairs(t)` 等典型形式一致。

之后通过 `TFORLOOP` 驱动循环，并同样把控制变量和用户可见循环变量都纳入局部变量体系中。

## 17. 表构造器：当前实现里最有工程含量的部分之一

表构造器同时包含：

- 哈希字段：`{x = 1, [k] = v}`
- 数组字段：`{1, 2, 3}`
- 最后一个字段的多返回值展开：`{1, f()}`

所以它的生成远比表面看起来复杂。

### 17.1 先发 `NEWTABLE`，再回填大小

实现先发：

```text
NEWTABLE A 0 0
```

等遍历完字段后，再回写：

- B：数组部分大小 `na`
- C：哈希部分大小 `nh`

### 17.2 哈希字段

哈希字段相对简单：

1. 计算 key
2. 计算 value
3. 发 `SETTABLE tableReg, rkKey, rkVal`

每次写完后会恢复 `freereg_`，避免临时寄存器泄漏影响后续字段。

### 17.3 数组字段

数组字段采用“连续寄存器积攒 + 批量 `SETLIST`”的策略。

大意是：

- 第 1 个数组元素放 `R(tableReg+1)`
- 第 2 个放 `R(tableReg+2)`
- ...
- 累积到一定数量或到末尾时，用 `SETLIST` 一次性写入表

这样比逐个 `SETTABLE` 更贴近 Lua 5.1 的实现方式，也更高效。

### 17.4 最后一个数组字段的多返回值展开

这是整个表构造器最关键的难点。

Lua 5.1 允许：

```lua
t = {1, 2, f()}
```

其中 `f()` 不是只放一个值，而是会把其所有返回值展开到数组尾部。

当前实现的处理方式很成熟：

1. 如果最后一个数组字段是 `CallExpr`，提前设置 `forcedCallBase_ = tableReg + tostore`
2. 这样 `CallExpr` 在生成时就会把调用基址对齐到数组字段目标区间
3. 最后阶段把 `CALL` 的 `C` 改成 `0`，表示返回全部值
4. 再发 `SETLIST tableReg, 0, c`，其中 `B=0` 表示把栈顶全部写入数组部分

对 `VARARG` 也采用类似思路：

- 改 `A` 到目标起始寄存器
- 改 `B=0` 表示复制全部 vararg

这部分如果没有 `forcedCallBase_` 的帮助，几乎一定会出现“多返回值展开位置不对”的问题。

## 18. 函数定义与闭包：为什么 `CLOSURE` 后还要跟伪指令

函数定义对应两类 AST：

- `FunctionExpr`
- `FunctionStmt`

两者核心流程一致：

1. 调用 `compileFunction()` 递归生成子函数 `Proto`
2. 把子 `Proto` 加入当前 `proto_`
3. 发 `CLOSURE`
4. 立刻发若干条 upvalue 绑定伪指令

### 18.1 `compileFunction()` 在做什么

它会创建一个新的子 `CodeGenerator`，并让它的 `parent_ = this`，然后：

- 建立新的 `Proto`
- 设置参数个数、是否 vararg、定义行号范围
- 把参数加入局部变量表
- 编译函数体
- 补隐式 `RETURN`
- 记录 upvalue 名称
- 写入调试元信息

这里的一个重要设计是：

> 子函数不是在父生成器的状态上继续写，而是使用独立生成器对象。

这样寄存器、局部变量、跳转链表、块作用域等状态都天然隔离，只通过 `parent_` 做 upvalue 解析。

### 18.2 为什么 `CLOSURE` 后要跟 `MOVE/GETUPVAL`

Lua 5.1 约定：`CLOSURE` 只说明“创建一个闭包，使用哪一个子 `Proto`”，但这个闭包具体捕获哪些 upvalue、每个 upvalue 来自哪里，需要紧随其后的伪指令来说明。

当前实现通过 `emitClosureUpvalues()` 发射：

- 若 upvalue 来自父函数局部变量：`MOVE 0, index, 0`
- 若来自父函数 upvalue：`GETUPVAL 0, index, 0`

这里的 A 字段固定为 0，是遵循 Lua 5.1 对 closure upvalue 伪指令的解释方式，而不是普通运行时意义上的 `MOVE/GETUPVAL`。

### 18.3 局部函数与全局/表成员函数

#### 局部函数

`local function f() end`

实现策略是：

1. 先为 `f` 分配局部变量寄存器
2. 直接把 `CLOSURE` 结果写入该寄存器
3. 激活局部变量

这样函数体可以正确捕获自己或后续作用域中的名字。

#### 全局函数 / 表成员函数

例如：

```lua
function f() end
function t.a.b:c() end
```

当前实现会：

- 对简单全局函数，创建闭包后发 `SETGLOBAL`
- 对表成员函数，先逐层把 `t.a.b` 读取到某个表寄存器，再 `SETTABLE tableReg, "name", closure`

这部分还兼顾了局部名、upvalue 名、全局名三种路径来源。

## 19. `luaK_storevar()`：赋值语义统一入口

这是一个很值得单独拎出来看的函数，因为它把“不同种类左值”的写回逻辑统一到了一处。

它实际上是在回答一个问题：

> 现在手里有一个值 `ex`，我该怎样把它写到变量 `var` 中？

根据 `var.kind` 不同，策略完全不同：

- `Local`：直接 `discharge(ex, varReg)`
- `Upval`：`SETUPVAL`
- `Global`：`SETGLOBAL`
- `Indexed`：`SETTABLE`

这也是为什么很多上层代码不需要直接关心“赋值目标到底是什么”，它只需要先把目标解析成一个 `ExprDesc`，然后统一交给 `luaK_storevar()`。

## 20. 代码块与 `break`：块管理为什么不能省

`enterBlock()` / `leaveBlock()` 看起来只是管理一个链表节点，实际上承担了三项关键职责：

1. 记录进入块时的 `nactvar_`
2. 记录该块内的 `break` 跳转链表
3. 在离开块时统一清理局部变量并修补 `break`

### 20.1 `break` 的工作方式

遇到 `break` 时，生成器会：

- 向外查找最近的 `isbreakable` 块
- 发一条 `jump()`
- 把它拼到该块的 `breaklist` 上

等到 `leaveBlock()` 时，再把这些跳转全部补到块尾部。

这种做法简单而稳定，比“在 `break` 发生时立即知道出口地址”更现实。

---

## 21. 调试信息：为什么不是可有可无

当前实现最后会调用 `attachDebugMetadata()`，把 `localVars_` 里的局部变量生命周期信息写回 `Proto`。

这意味着生成器不仅能产出“能跑的字节码”，还能产出“能被调试器、反汇编器、错误报告使用”的元数据。

此外还有两块调试信息来源：

- `currentLine_` -> `addLineInfo()`
- `upvalues_` -> `addUpvalueName()`

如果少了这些信息，后续调试将会明显更困难。

## 22. 这份实现里最值得注意的几个“坑点”

阅读 `codegen.cpp` 时，下面这些点尤其值得关注，因为它们都是真实容易出错的地方。

### 22.1 不能随便改 `CALL` 的 A 参数

`CALL A B C` 中的 A 不是单纯“结果寄存器”，而是整个调用帧的基址：

- 函数在 `R(A)`
- 参数在 `R(A+1)...`
- 返回值也从 `R(A)` 开始覆盖

所以像局部初始化、多返回值赋值、表构造器展开这类场景，若目标寄存器不同，通常应该：

- 改 `C`
- 或者在调用后补 `MOVE`

而不是直接乱改 A。

### 22.2 `Relocatable` 与 `NonRelocatable` 的区别必须守住

如果一个表达式已经真正落在寄存器里，却还把它当成 `Relocatable` 修改 A，或者反过来，本来能改写 A 的结果却额外生成 `MOVE`，都会让寄存器布局变得混乱。

### 22.3 短路逻辑不能只看真假，还要保留原值

Lua 的 `and` / `or` 返回的不是纯布尔，而是操作数原值。若按 C 风格思维去生成，很容易得到错误语义。

### 22.4 最后一个表达式的多返回值规则非常特殊

无论在：

- 赋值
- 局部声明
- 表构造器
- 返回语句

Lua 都对“最后一个表达式是否扩展”为多个值有特殊规则。这是很多实现偏差的来源。

### 22.5 `freereg_` 与 `nactvar_` 的关系不能乱

很多 bug 最终都不是指令本身写错，而是某条语句结束后 `freereg_` 没回到合理位置，导致下一条语句在错误寄存器区继续工作。

## 23. 当前实现与 Lua 5.1 的对齐点

从注释和实现风格可以明显看出，这份代码生成器在很多关键点上都努力向 Lua 5.1 对齐，尤其包括：

- `dischargejpc()` 先于发指令
- `ExprDesc` 风格的表达式状态机
- `Relocatable` / `NonRelocatable` / `Jump` / `Call` / `Vararg` 的区分
- `patchtohere()` 与跳转链表模式
- `SELF`、`SETLIST`、`FORPREP/FORLOOP`、`TFORLOOP` 的使用方式
- `CLOSURE` 后紧跟 upvalue 伪指令

这意味着后续如果要继续补功能，最好的路线通常不是凭感觉扩展，而是继续参考 Lua 5.1 原始实现的同名逻辑。

## 24. 当前实现已知限制与可继续完善的方向

从代码中可以直接看出几项尚未完全覆盖或仍可增强的点。

### 24.1 `repeat-until` 尚未实现

当前 `emitStmt(const RepeatStmt&)` 直接抛异常。

### 24.2 `checkStack()` 里还有 `MAXSTACK` TODO

现在会更新 `maxStackSize`，但还没有像 Lua 5.1 那样在超限时抛出明确的语法/复杂度错误。

### 24.3 一些 Lua 5.1 细节语义仍可继续打磨

例如多返回值在不同上下文的边角语义、尾调用相关优化、更多官方字节码级别小优化等。

不过就现有代码而言，整体框架已经足够完整，继续增强更多是在“补全细节”，而不是“推倒重来”。

## 25. 建议的阅读顺序

如果你是第一次读这份代码，建议按下面顺序看：

1. `codegen.hpp`：先熟悉 `ExprKind`、`ExprDesc`、`BlockInfo`、`UpvalueCapture`
2. `generate()`：先看顶层入口如何初始化状态
3. `discharge()`、`exp2AnyReg()`、`exp2RK()`、`exp2Val()`：理解表达式如何落地
4. `emitExpr(const CallExpr&)`：理解调用寄存器布局
5. `emitStmt(const LocalStmt&)`、`emitStmt(const AssignStmt&)`：理解单值/多值赋值
6. `jump()` / `patchtohere()` / `luaK_goiftrue()`：理解跳转模型
7. `compileFunction()` 与 `emitClosureUpvalues()`：理解闭包生成
8. `emitExpr(const TableExpr&)`：理解复杂容器初始化

按这个顺序阅读，心智负担会小很多。

## 26. 一句话总结

这份 `CodeGenerator` 的本质，不是“把 AST 节点一对一翻译成指令”，而是：

> 在严格维护寄存器布局、表达式状态和跳转链表的前提下，把 Lua 语义稳定地映射为 Lua 5.1 风格字节码。

如果只把它看成“语法树遍历器”，会低估它的复杂度；如果把它看成“一个寄存器调度器 + 控制流回填器 + 函数原型组装器”，就更容易读懂它为什么会写成现在这样。
